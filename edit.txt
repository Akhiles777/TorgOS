

## Задача

В StoreOS нужен раздел «Камеры»: владелец смотрит свой магазин с телефона или ноутбука, живьём и в записи с перемоткой.

Первое железо для отладки — **Dahua DHI-HCVR5108C-S2**: 8-канальный HDCVI-видеорегистратор 2015 года, аналоговые камеры подключены к нему коаксиалом. Регистратор отдаёт RTSP. Архив пишется на его собственный жёсткий диск.

Архитектуру делай не под одно это устройство, а под любой регистратор с RTSP — Dahua, Hikvision, китайские безымянные. Различия выносим в конфигурацию, а не в код.

## Стек

Существующий проект: Next.js 16 App Router, TypeScript strict, Prisma + PostgreSQL, кастомный `server.mjs` с `ws`, PM2, Nginx, Ubuntu 26.04 на VDS Timeweb.

Добавляем **go2rtc** — отдельный процесс, забирает RTSP и отдаёт WebRTC/HLS в браузер. Не пиши свой транскодер на ffmpeg, это решённая задача.

## Топология — ключевое решение

Регистратор стоит в магазине за NAT провайдера. Сервер в дата-центре к нему подключиться не может. Порты наружу открывать **запрещено**: регистраторы Dahua со старой прошивкой массово сканируют и взламывают, мы не можем повесить этот риск на клиента.

Реализуем **агентскую схему**:

- В магазине рядом с регистратором стоит мини-ПК или Raspberry Pi — «агент точки»
- На агенте работает go2rtc, он берёт RTSP локально по LAN
- Агент сам инициирует исходящее соединение к нашему серверу (WireGuard-туннель или WebSocket-канал — предложи вариант и обоснуй)
- Сервер обращается к go2rtc агента через этот туннель

Сделай так, чтобы схему можно было заменить: для клиента, у которого есть белый IP и он осознанно на это идёт, должен работать прямой режим. Тип подключения — поле в модели камеры.

## Модель данных

```prisma
model CameraDevice {          // видеорегистратор или IP-камера
  id            String   @id @default(cuid())
  storeId       String
  name          String            // «Регистратор в подсобке»
  vendor        String            // dahua | hikvision | generic
  host          String            // адрес в локальной сети магазина
  port          Int      @default(554)
  username      String
  passwordEnc   String            // шифруем, не храним в открытом виде
  connection    String            // agent | direct
  agentId       String?
  isActive      Boolean  @default(true)
}

model Camera {                // отдельный канал
  id            String   @id @default(cuid())
  deviceId      String
  channel       Int               // номер канала на регистраторе
  name          String            // «Касса», «Вход», «Молочный отдел»
  position      Int               // порядок в сетке
  isActive      Boolean  @default(true)
}

model StoreAgent {
  id            String   @id @default(cuid())
  storeId       String
  token         String   @unique  // для авторизации агента
  lastSeenAt    DateTime?
  version       String?
}
```

**Пароли от регистратора шифруй** (AES-256-GCM, ключ в переменной окружения), не храни plaintext. Это чужое оборудование в чужом магазине.

## Экраны

**`/admin/cameras` — сетка живого просмотра**
- Плитки 2×2 или 3×3, переключение количества
- Клик по плитке — на весь экран
- Отметка «нет сигнала», если поток не поднялся
- Кнопка «Архив» на каждой плитке

**`/admin/cameras/[id]/archive` — просмотр записи**
- Выбор даты в календаре
- Горизонтальная временная шкала на 24 часа с отметками, где есть запись
- Перемотка кликом по шкале, скорости 1×, 2×, 4×
- Скачивание фрагмента (укажи промежуток → получи файл)

**Мобильная вёрстка обязательна** — владелец смотрит с телефона.

## Технические требования

**Потоки.** Регистратор отдаёт основной поток (`subtype=0`) около 3500 Kb/s на канал — восемь каналов это 25 Мбит/с, у магазина такого исходящего канала нет. Правила:
- в сетке всегда substream (`subtype=1`)
- основной поток только в полноэкранном режиме и только для одной камеры
- поток поднимается **по требованию**, когда камеру реально смотрят, и гасится через 30 секунд после закрытия

**URL потоков Dahua** (проверь на реальном устройстве, у старых прошивок бывают отличия):
```
Живой:  rtsp://USER:PASS@HOST:554/cam/realmonitor?channel=N&subtype=1
Архив:  rtsp://USER:PASS@HOST:554/cam/playback?channel=N&starttime=YYYY_MM_DD_HH_MM_SS&endtime=YYYY_MM_DD_HH_MM_SS
```
Для Hikvision формат другой — вынеси шаблоны URL в конфиг по вендору, не хардкодь в компонентах.

**Живой просмотр** — WebRTC через go2rtc, задержка меньше секунды. HLS как фолбэк, если WebRTC не поднялся (бывает за корпоративными NAT).

**Поиск записей по дате.** У Dahua есть HTTP CGI-API для получения списка файлов архива. Если не заработает на этой прошивке — деградируй: показывай шкалу целиком и просто запрашивай плейбек с нужного времени, без предварительной отметки «где есть запись».

**Важно про часы регистратора.** На нашем устройстве системное время сбито (стоит 2000 год), из-за чего архив по датам не ищется. Добавь в интерфейс проверку: при подключении устройства сравнивай его время с нашим, и если расхождение больше пяти минут — покажи предупреждение «часы регистратора сбиты, архив по датам работать не будет» со ссылкой на инструкцию. Эта проблема встретится у половины клиентов.

## Права доступа

- **OWNER** — все камеры всех своих точек
- **ADMIN** — камеры своей точки
- **CASHIER** — не видит раздел вообще. Кассир не должен смотреть камеры, в том числе на себя

Доступ к камерам проверяй на сервере при каждом запросе потока, а не только скрытием пунктов меню.

!!! Это решение должно быть общедоступным, что бы можно было самому все настроить по инструкции и так-же спросить ИИ именно про эту тему и он что бы помог все подключить именно к нашей системе!

## Чего не делать сейчас

- Никакой аналитики видео, распознавания, детекции краж. Только просмотр. ИИ-слой поверх — отдельная задача, для неё нужен работающий транспорт
- Не хранить видео на нашем сервере. Архив живёт на диске регистратора. Хранение чужого видео — это и деньги за место, и совсем другая ответственность по 152-ФЗ
- Не открывать порты регистратора в интернет ни в каком виде
- Не тащить платные SDK и облачные сервисы вроде Dahua DMSS / P2P-облака вендора

## Порядок работы

1. План — покажи, согласуем
2. Схема БД + миграция + шифрование паролей устройств
3. Установка и конфигурация go2rtc, проверка потока с реального регистратора (я дам доступ по локальной сети)
4. Агент точки: как ставится, как авторизуется, как держит туннель. Это отдельный небольшой компонент, опиши его установку в двух командах для клиента
5. Экран живого просмотра
6. Архив с временной шкалой
7. Отчёт: что сделано, какие решения принял сам, что проверить руками, что не заработало на этой прошивке

Начинай с плана.
