## ⚠️ Те же ограничения по данным, что и раньше

В production-базе живут данные реального работающего магазина. Восстановить нечем.

- Никогда: `prisma migrate reset`, `db push --force-reset`, `npm run db:seed`, любые правки `prisma/seed.ts` — он безусловно чистит базу
- Все миграции только аддитивные: новые таблицы, nullable-поля, новые значения enum. Никаких DROP, переименований, обязательных полей без дефолта
- Поведение существующих моделей для розницы и общепита не меняется
- Перед первой миграцией — напомни мне сделать дамп

## Что строим

Интернет-магазин продуктов из семейного гастронома: каталог, корзина, оформление заказа, самовывоз или доставка. Плюс ИИ-помощник, который собирает корзину под блюдо. Плюс приём заказов через WhatsApp.

**Ключевая идея:** магазин уже работает на StoreOS — касса, приёмка, остатки в одной системе. Значит витрина показывает **живой остаток**, а не вчерашнюю выгрузку. Это главное преимущество, архитектура должна его обеспечивать, а не имитировать.

## Архитектура — отдельный домен, общий код

Проект **не выносится в отдельный репозиторий**. Тот же Next.js, та же база, тот же процесс. Разделение — по домену:

- `storeos.online` — существующий продукт (лендинг, касса, админка, `/root`)
- новый домен (я его куплю и направлю на этот же сервер) — витрина магазина

**Реализация:** middleware определяет `host` и переписывает путь в сегмент `/shop`. Nginx проксирует оба домена на тот же порт 3000. Разные `layout` и разное оформление у витрины и у StoreOS.

Проверь и предложи в плане, как это чище сделать в Next.js 16 App Router — route groups с middleware rewrite или отдельный сегмент. Обоснуй выбор.

**Витрина привязана к одной точке** (`Store`) через переменную окружения или запись в базе. Архитектурно не закрывай возможность нескольких витрин потом, но сейчас не усложняй — одна точка, один домен.

## Модель данных

Каталог витрины — это **существующие `Product` того же магазина**. Не дублируй номенклатуру. Товар попадает на витрину, если у него есть фото, цена и остаток больше буфера.

Новые модели:

```prisma
model ShopSettings {          // одна запись на точку
  id              String  @id @default(cuid())
  storeId         String  @unique
  isOpen          Boolean @default(false)     // приём заказов включён
  freeDeliveryFrom Decimal @db.Decimal(10,2)  // 500
  deliveryFee     Decimal @db.Decimal(10,2)   // 80
  minOrder        Decimal @db.Decimal(10,2)
  stockBuffer     Int     @default(2)         // не показывать, если остаток ниже
  deliveryZone    Json?                       // радиус или список районов
  phone           String?
  address         String?
}

model ShopProduct {           // витринные данные поверх Product
  id           String  @id @default(cuid())
  productId    String  @unique
  imageUrl     String?
  description  String?
  isPublished  Boolean @default(false)
  position     Int     @default(0)
  shopCategory String?                        // категория витрины ≠ категория склада
}

model Customer {
  id         String   @id @default(cuid())
  phone      String   @unique
  name       String?
  createdAt  DateTime @default(now())
  addresses  CustomerAddress[]
  orders     ShopOrder[]
}

model CustomerAddress {
  id         String  @id @default(cuid())
  customerId String
  street     String
  building   String
  apartment  String?
  entrance   String?
  floor      String?
  comment    String?
  isDefault  Boolean @default(false)
}

model ShopOrder {
  id             String          @id @default(cuid())
  number         Int             @default(autoincrement())
  storeId        String
  customerId     String
  addressId      String?                       // null = самовывоз
  fulfillment    Fulfillment                   // PICKUP | DELIVERY
  status         ShopOrderStatus
  slotFrom       DateTime?
  slotTo         DateTime?
  itemsTotal     Decimal         @db.Decimal(10,2)
  deliveryFee    Decimal         @db.Decimal(10,2)
  total          Decimal         @db.Decimal(10,2)
  paymentMethod  ShopPayment                   // CASH | CARD_ON_DELIVERY
  comment        String?
  source         OrderSource                   // WEB | WHATSAPP
  saleId         String?         @unique       // связь с чеком после выдачи
  createdAt      DateTime        @default(now())
  items          ShopOrderItem[]
}

model ShopOrderItem {
  id            String  @id @default(cuid())
  orderId       String
  productId     String
  nameAtOrder   String                         // снимок названия
  quantity      Decimal @db.Decimal(10,3)      // заказано
  pickedQuantity Decimal? @db.Decimal(10,3)    // фактически собрано (развесной!)
  priceAtOrder  Decimal @db.Decimal(10,2)
  status        ItemStatus                     // OK | MISSING | REPLACED
  replacedById  String?                        // чем заменили
}

enum Fulfillment      { PICKUP DELIVERY }
enum ShopOrderStatus  { NEW CONFIRMED PICKING READY DELIVERING DONE CANCELLED }
enum ShopPayment      { CASH CARD_ON_DELIVERY }
enum OrderSource      { WEB WHATSAPP }
enum ItemStatus       { OK MISSING REPLACED }
```

Все новые модели зарегистрируй в `server/tenant.ts` по установленному паттерну. `Customer`/`CustomerAddress` — это клиенты конкретной точки, скоупь через `store`.

## Ключевое: остатки и резервирование

Здесь легко сделать неправильно, поэтому явно:

**Не декрементируй `Product.stock` при оформлении заказа.** Магазин продолжает торговать в зале, касса списывает остаток. Если сайт тоже начнёт списывать, начнутся расхождения и минусовые остатки.

Правильно:
- витрина показывает товар только если `stock > shopSettings.stockBuffer` (буфер защищает от гонки с продажами в зале)
- при оформлении остаток **не трогается** — заказ это намерение, не продажа
- реальное списание — при сборке заказа, когда сборщик подтвердил фактическое количество
- в этот момент создаётся `Sale` через **существующий** `commitSale` (или `createSaleRecord`, если к тому времени он уже вынесен модулем общепита) — одна точка создания чека на весь проект, не дублируй

**Развесной товар.** Клиент заказывает «≈1 кг», видит пометку что цена ориентировочная. Сборщик вводит фактический вес в `pickedQuantity`, сумма пересчитывается. Расхождение больше 15% — пометить для согласования с клиентом.

## Экраны витрины (новый домен)

- **Главная** — категории, популярное, поиск, кнопка ИИ-помощника
- **Каталог** — сетка товаров с фото(нужно что бы нейросеть запустила поиск по штрих кодам и тд и дала ссылку на изображение продукта, или по умолчанию заполнить иконками), ценой, кнопкой в корзину. Мобильная вёрстка первична: заказывают с телефона
- **Карточка товара**
- **Корзина** — позиции, сумма, сколько не хватает до бесплатной доставки (это повышает чек, сделай заметно)
- **Оформление** — телефон, имя, самовывоз или доставка, адрес, слот, способ оплаты, комментарий. **Без обязательной регистрации** — вход по номеру телефона с кодом или вообще без входа на первом заказе. Регистрация убивает конверсию у этой аудитории
- **Мои заказы** — статус, повтор заказа одной кнопкой (самая используемая функция в продуктовой доставке)

Дизайн витрины — **свой, не токены StoreOS**. Это продукт для конечного покупателя, а не B2B-инструмент. Предложи дизайн-план отдельно, до вёрстки: палитра, шрифты, сетка. Из мира продуктового магазина у дома, но современно. Никаких дефолтных SaaS-обликов.

## Экраны для магазина (внутри StoreOS, `/admin/shop`)

- **Заказы** — лента новых, звуковое уведомление о новом заказе (магазин не сидит уставившись в экран)
- **Экран сборщика** — открыт на телефоне, список позиций, отметить собрано / нет в наличии / заменено, ввод фактического веса. По завершении — итоговая сумма и создание чека
- **Каталог витрины** — какие товары опубликованы, загрузка фото, описания, категории витрины
- **Настройки** — приём заказов вкл/выкл, пороги доставки, слоты, зона

## ИИ-помощник

Задача: «что нужно для хинкала на 4 человек» → список товаров **из реального каталога с реальным остатком** → добавить всё в корзину одной кнопкой.

**Жёсткое требование: модель не придумывает товары.** Порядок работы:
1. Модель разбирает запрос в список ингредиентов с количествами
2. Каждый ингредиент ищется по каталогу этой точки (по названию и категории)
3. В ответ идут **только найденные и доступные** позиции
4. Чего нет — честно показывается «этого у нас нет», без подмены

Если реализуешь через function calling — модель вызывает поиск по каталогу, а не генерирует названия. Опиши в плане, как именно.

Контроль стоимости: кэшируй ответы по частым блюдам, ограничивай длину контекста, не гоняй весь каталог в промпт.

## WhatsApp через GreenAPI

Приём заказов в мессенджере: клиент пишет, ассистент помогает собрать корзину, клиент подтверждает, заказ падает в ту же ленту, что и с сайта (`source: WHATSAPP`).

Требования:
- вебхук от GreenAPI на входящие сообщения, отдельный роут
- состояние диалога в базе, не в памяти процесса (перезапуск PM2 не должен терять корзины)
- тот же слой подбора товаров, что у веб-ассистента — не дублируй логику
- финальное подтверждение обязательно: показать состав, сумму, адрес → клиент подтверждает → заказ создан
- команда «оператор» переключает на живого человека и останавливает бота для этого чата
- ключи GreenAPI — в `.env`, не в коде

**Отдельно предупреди меня в отчёте:** GreenAPI это неофициальный доступ к WhatsApp, номер может быть заблокирован. Нужна отдельная SIM, без рассылок, отвечаем только тем, кто написал первым.
